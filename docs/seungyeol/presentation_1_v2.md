# 1차 발표 v2: Meerkit, 어떤 프로젝트든 받쳐 주는 기반

> 청중: 강사님, 운영팀 매니저, 부트캠프 수강생
> 기준 시간: **약 12분** (발표 10분 + 질문 2분). 슬라이드는 **13장**.
> v1([presentation_1.md](presentation_1.md))에서 달라진 점: **"AI 서비스용"이 아니라 "어떤 프로젝트든 쓰는 인증·권한 기반"** 으로 포지션을 바꿨고, 대본을 말하듯 편하게 다시 썼고, 슬라이드 구성을 새로 잡았습니다.

## 0. 이 발표가 전달할 한 문장

> **"어떤 프로젝트를 만들든 가입·로그인·권한 관리는 똑같이 필요하다. 그걸 템플릿으로 만들어 두고, Meerkit이 밑에서 받쳐 준다."**

끝났을 때 청중이 이 한 문장만 기억하면 성공입니다.

**포인트 세 개 (이것만 반복해서 말하세요)**

1. **AI 서비스가 아니어도 쓴다.** 쇼핑몰, 커뮤니티, 사내 도구, 예약 서비스 어디든. AI는 "있으면 붙이는 선택 부품"일 뿐이다.
2. **유저 인증과 권한 관리를 템플릿으로 제공한다.** 가입, 로그인, 비밀번호 재설정, 역할, 관리자 화면까지 미리 만들어 둔다.
3. **우리는 "기반"이다.** 프로젝트가 뭐든 Meerkit이 바닥을 깔고, 개발자는 그 위에 자기 서비스만 올린다.

## 0-2. 정직하게 말할 것 (먼저 말해서 신뢰를 지키세요)

- **백엔드는 아직 구현 전**입니다. 화면(UI)과 문서는 완성, 서버 연동은 다음 단계라고 먼저 말하세요.
- `npx create-meerkit` 같은 **한 줄 세팅은 "계획"**입니다. "된다"가 아니라 "다음에 보여 드린다"로 말하세요.
- **AI 컴포넌트는 UI만** 만들었습니다. 음성 변환, 응답 생성, 사용량 집계는 서비스(또는 추후)에서 연결합니다.
- 로그인 잠금은 브라우저 쪽 안내용이라 **서버에서도 막아야** 합니다. "보안이 끝났다"가 아니라 "서버가 할 일을 문서에 적어 뒀다"고 말하세요.

## 슬라이드별 구성안과 대본

### 슬라이드 1. 표지 (30초)

**화면:** 로고 + `Meerkit` + 한 줄 "어떤 프로젝트든 받쳐 주는 인증·권한 스타터킷" + 이름, 날짜
**대본:**
> "안녕하세요, ○○○입니다. 오늘은 저희가 만들고 있는 **Meerkit**을 소개할게요. 한 줄로 말하면, 프로젝트가 뭐든 간에 **밑에서 받쳐 주는 기반**입니다. 지금까지 뭘 만들었는지 보여 드리고, 다음 주에는 이걸로 진짜 서비스를 하나 세워 보겠습니다."

### 슬라이드 2. 문제 (1분)

**화면:** 제목 "프로젝트는 매번 다른데, 시작은 늘 똑같다" + 아이콘 5개 (회원가입 / 로그인 / 비밀번호 찾기 / 권한 / 관리자 화면)
**대본:**
> "새 프로젝트를 시작하면 이상하게 시작이 늘 똑같아요. 쇼핑몰이든, 커뮤니티든, AI 서비스든 제일 먼저 만드는 게 회원가입, 로그인, 비밀번호 찾기, 권한, 관리자 화면입니다. 정작 내가 만들고 싶은 핵심 기능은 한참 뒤에 나오죠. 게다가 이건 보안이랑 붙어 있어서, 매번 새로 만들 때마다 실수할 위험도 같이 따라옵니다. 저희도 이 시간이 꽤 아까웠어요."

> 발표 팁: 실제로 겪은 일을 한 문장 더하면 공감이 훨씬 커집니다.

### 슬라이드 3. 해결: Meerkit (1분 15초) ★ 핵심 포인트

**화면:** 큰 문장 "AI 서비스가 아니어도 됩니다." 아래에 프로젝트 예시 카드 4개 — 쇼핑몰 / 커뮤니티 / 사내 도구 / 예약 서비스 / (작게) AI 서비스. 웰컴 페이지 스크린샷
**대본:**
> "그래서 이 공통 부분을 **통째로 템플릿으로 만들었어요.** 이름이 Meerkit이에요. 먼저 오해 하나만 풀고 갈게요. 저희 주제에 AI가 들어 있어서 'AI 서비스 전용이구나' 하실 수 있는데, **전혀 아니에요.** 로그인과 권한이 필요한 프로젝트라면 뭐든 쓸 수 있습니다. 쇼핑몰이든, 커뮤니티든, 사내 관리 도구든요. AI 부품은 '필요하면 붙이는 선택 상자' 정도로 생각해 주세요."

### 슬라이드 4. 구조: 바닥을 까는 기반 (1분 15초) ★ 강사님 포인트

**화면:** 3층 그림
```
┌─ 내 서비스 (쇼핑몰, 커뮤니티, … 개발자가 만드는 부분) ─┐
├─ Meerkit (가입·로그인·권한·관리자 화면·UI 부품) ─────┤  ← 우리가 제공
└─ 서버(FastAPI) · DB(PostgreSQL) ─────────────────────┘
```
옆에 "킷 코드(`src/meerkit`)와 서비스 코드는 폴더가 분리"
**대본:**
> "구조는 건물 같아요. 맨 위에 **내 서비스**가 있고, 그 아래 바닥을 Meerkit이 깔아 줍니다. 가입, 로그인, 권한, 관리자 화면이 여기에 있어요. 그 밑은 서버와 데이터베이스고요. 중요한 건 **킷 코드와 서비스 코드를 폴더로 딱 나눴다**는 거예요. 그래서 개발자는 자기 서비스만 신경 쓰면 되고, 킷이 업데이트돼도 내 서비스가 깨지지 않습니다."

### 슬라이드 5. 누가 쓰나 (45초)

**화면:** 사용자 3종 그림 — 서비스 개발자 / 서비스 관리자 / 서비스 사용자
**대본:**
> "쓰는 사람은 세 부류예요. 킷을 가져다 쓰는 **개발자**, 그 서비스를 운영하는 **관리자**, 그리고 서비스를 이용하는 **일반 사용자**. 일반 사용자는 가입하고 로그인하고, 관리자는 멤버를 찾고 권한을 바꾸고, 개발자는 이 모든 걸 **설정 파일 하나**로 조절합니다."

### 슬라이드 6. 범위: 넣은 것 / 뺀 것 (1분 15초) ★ 매니저 포인트

**화면:** 두 열 표

| 넣은 것 (기본) | 선택 부품 (UI만) | 뺀 것 (의도적) |
| --- | --- | --- |
| 회원가입·로그인, 비밀번호 재설정 | AI 입력창, 생각 중 표시, 음성 입력 | 소셜 로그인, 2단계 인증 |
| 역할 4종 (MASTER/OWNER/VIEWER/WRITER) | 멤버 AI 사용량 차트 | 세부 권한(permission) 테이블 |
| 관리자: 멤버 검색·필터·역할 변경 | 로딩 9종, 첨부파일, 주소 검색 | 프로필 이미지 업로드 |
| 로그인 잠금, 약관 동의, 이메일 인증(선택) | | |

**대본:**
> "범위는 세 칸으로 나눠서 말씀드릴게요. 왼쪽이 **기본으로 들어 있는 것**, 인증과 권한과 관리자 화면이에요. 가운데는 **있으면 편한 선택 부품**인데, AI 입력창이나 음성 입력 같은 게 여기 있어요. 이건 화면만 만든 거라 AI 호출은 서비스에서 연결합니다. 오른쪽은 **일부러 뺀 것**이에요. 소셜 로그인이나 세부 권한은 다음으로 미뤘습니다. 다 하려다 아무것도 못 끝내는 것보다, 끝까지 쓸 수 있는 범위를 먼저 완성하는 쪽을 골랐어요."

> 매니저를 위한 한마디: "뺀 것"을 말하는 게 계획이 구체적이라는 신호입니다.

### 슬라이드 7. 기획 과정 (1분) ★ 강사님 포인트

**화면:** 타임라인 — 팀 회의 → 테이블 설계 → 구조 설계 → 프론트 구현. 가운데에 `users ↔ roles` 그림
**대본:**
> "기획은 팀 회의에서 시작했어요. 화이트보드에 회원 테이블을 그리면서 세 가지를 정했습니다. 첫째, 로그인은 이메일이 아니라 **아이디**로. 둘째, 권한은 사용자 테이블에 박지 않고 **roles 테이블로 분리**. 셋째, 탈퇴는 진짜 지우지 않고 **삭제 시각만 기록**. 이유는 간단해요. 권한이 늘어도 사용자 테이블을 안 고쳐도 되고, 나중에 이력도 남길 수 있거든요."

### 슬라이드 8. 설계 원칙 세 가지 (1분) ★ 강사님 포인트

**화면:** 카드 3장
1. 권한은 **서버가 최종 판단** (화면은 편의)
2. 액세스 토큰은 **메모리**, 리프레시 토큰은 **httpOnly 쿠키**
3. 설정은 **`meerkit.config.ts` 한 파일**

**대본:**
> "지킨 원칙이 세 가지예요. 하나, 버튼을 숨기는 건 보호가 아니라서 **권한은 항상 서버가 다시 검사**해요. 둘, 토큰은 훔쳐 가기 어렵게 하나는 메모리에만, 하나는 자바스크립트가 못 읽는 쿠키에 둬요. 셋, 개발자가 코드를 뜯지 않고 **설정 파일 하나**로 잠금 횟수, 가입 항목, 테마, 로딩 모양까지 바꾸게 했어요."

## 말하기 요령

- 슬라이드 한 장에 **메시지 하나.** 제목은 "~이다" 문장으로. 예: "프로젝트는 달라도 시작은 같다."
- **화면을 읽지 마세요.** 슬라이드엔 단어와 그림만, 문장은 입으로.
- 숫자 세 개만 기억시키세요: **역할 4종 / 문서 41페이지 / 설정 파일 1개.**
- "AI 서비스가 아니어도 된다"는 말은 **슬라이드 1, 3, 13에서 세 번** 반복하세요.
- 데모는 **누르고 나서 말하세요.** 화면이 바뀌는 중에 말이 겹치면 놓칩니다.
- 첫 30초와 마지막 30초는 **외워서** 말하세요.
- 리허설은 소리 내서 두 번, 한 번은 시간 재고 한 번은 데모 포함.

## 2차 발표와 연결하기

1차 마지막에 던진 약속(가상 서비스를 기반 위에 올리기)을 2차에서 증명합니다. 지금부터 정해 두면 좋은 것:

1. **가상 서비스 이름과 한 줄 소개.** AI가 아닌 서비스(예: 스터디룸 예약)를 하나 고르면 "AI 전용이 아니다"를 몸으로 증명할 수 있습니다.
2. 그 서비스가 켤 킷 기능 (로그인, 관리자 화면, 역할)
3. 2차 데모 전에 **백엔드 연동 + 한 줄 세팅**이 최소한 동작하는지

2차 첫 장은 "지난주 약속", 마지막은 "킷 없이 만들 때와 걸리는 시간 비교"로 끝내면 효과적입니다.
